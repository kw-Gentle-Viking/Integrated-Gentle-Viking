# 프로젝트 개요 (발표용 자료, 2026-10-27 기준)

이 문서는 README의 구조 설명에 실제 운영·실험 데이터를 더해, 프로젝트를 처음 보는 사람에게
"무엇을 왜 이렇게 만들었고, 실제로 뭘 확인했는가"를 설명하기 위해 정리했다. 구현 세부사항(API
경로, 테이블명 등)보다 설계 의도와 데이터 해석을 중심으로 썼다.

## 1. 문제 정의

코스피 상위 종목에 대해 "다음 거래일 가격이 오를지/내릴지"를 예측하는 AI를 만들고, 그 예측이
실제로 주문까지 이어지는 자동매매 시스템을 끝까지(end-to-end) 구축해서 검증하는 것이 목표다.
"AI가 잘 맞춘다"는 주장만으로는 부족하다고 보고, 실제 장중 데이터로 (1) 예측 파이프라인이
끊기지 않고 도는지, (2) 예측이 백엔드·전략을 거쳐 실제 주문 판단까지 이어지는지, (3) 그 판단이
타당한지를 모의투자 계좌로 실측했다.

## 2. 왜 이렇게 설계했는가

### 2.1 예측 대상을 "절대 수익률"이 아니라 "상대 순위"로 잡은 이유

처음엔 "내일 수익률이 플러스/마이너스"를 직접 예측하려 했다. 그런데 하루 단위 개별 종목
수익률은 거의 노이즈에 가깝고, 고정된 임계값으로 매수/관망/매도를 나누면 어떤 날은 전 종목이
관망, 어떤 날은 전 종목이 매수로 쏠리는 문제가 있었다. 그래서 최종적으로 **매일 그날 거래된
종목들 사이에서 상대적으로 수익률이 높은 30%는 매수, 낮은 30%는 매도, 나머지는 관망**으로
라벨을 다시 정의했다(cross-sectional quantile label). "이 종목이 오늘 다른 종목들보다 나은가"를
묻는 쪽이 "오늘 수익률이 양수인가"를 묻는 쪽보다 예측하기 쉬웠고, 실제로 성능 지표(아래 3.2절)로
도 확인됐다.

### 2.2 왜 TFT(Temporal Fusion Transformer)인가

시계열(가격·수급·매크로 지표 등 60거래일치)과 정적 특성(종목이 어느 업종인지, 코스피/코스닥인지)을
같은 모델이 같이 다뤄야 했다. TFT는 이 둘을 구조적으로 분리해서 입력받는 설계라, "이 종목의
원래 성격"과 "오늘 들어온 새로운 정보"를 모델 내부에서 구분해 학습할 수 있다는 점이 맞았다.
다만 이 분리 구조가 역설적으로 문제를 만들기도 했다 — 3.3절에서 다룬다.

### 2.3 왜 모의투자부터인가, 왜 전략에 보수적인 기술조건을 더했는가

실거래 전에 "예측 → 전달 → 주문 판단 → 체결"이 끊기지 않고 도는지부터 확인하는 게 우선이라고
봤다. 그래서 한국투자증권 모의투자 계좌로 전체 경로를 구축했다. 또한 AI 확신도만으로 바로
주문을 내지 않고, 전략(`ultra_safe`)이 추세·과매도/과매수·변동성 밴드 같은 기술적 조건을 한 번
더 확인해야 실제 주문으로 이어지게 설계했다 — AI 신호 하나만 믿고 바로 매매하는 구조의 위험을
낮추기 위한 의도적인 선택이다. 이 설계가 실제로 어떤 결과를 만들었는지는 4절에서 데이터로
확인한다.

### 2.4 전체 구조

```
운영 데이터 수집(코스피 350종목, 1분·5분·일봉·수급·매크로)
      │
      ▼
AI 학습용 DB(200종목) — 매일 피처 재계산
      │
      ▼
AI 추론 서버 — 5분마다 최신 입력으로 매수/관망/매도 확률 계산
      │  (예측 결과 전달)
      ▼
백엔드 — 예측 저장, 자동매매 루프(확신도 확인 → 전략 필터 → 리스크 한도 → 주문)
      │
      ├──▶ 프론트엔드 (종목 선택, 포트폴리오 확인)
      └──▶ 한국투자증권 모의투자 API (잔고 조회, 주문, 체결)
```

## 3. 모델을 만드는 과정에서 확인한 것 (데이터)

### 3.1 체계적 비교 실험

하이퍼파라미터 탐색(수십 개 조합) → 피처 제거 실험(ablation) → 라벨 정의 비교(절대 임계값 vs
상대 순위 vs 변동성 정규화) → 정적변수 처리 방식 비교까지 단계적으로 비교했다. 예를 들어 같은
구조에서 라벨만 "고정 임계값"에서 "상대 순위"로 바꿨을 때 검증 성능(timing IC, 아래에서 설명)이
+0.0481 → **+0.0732**로 뚜렷하게 좋아졌다 — 이게 2.1절에서 설명한 라벨 재정의가 실제로 유효했다는
근거다.

*timing IC란*: 모델 점수(매수확률 − 매도확률)에서 "그 종목이 평소에 받는 평균 점수"를 뺀 나머지가,
다음날 실제 수익률 순위와 얼마나 일치하는지를 재는 지표다(상관계수, −1~+1). 종목 고유의 특성이
아니라 "오늘 뭔가 달랐는가"를 얼마나 잘 잡아내는지를 보려는 지표라서, 이 프로젝트의 핵심 성과
지표로 썼다.

### 3.2 최종 선정 모델 (2026-10-02)

| 구분 | 값 |
|---|---|
| 검증(val_2024) timing IC | **+0.0732** |
| 미래 구간(OOT_2026) timing IC | **+0.0293** |
| 시드 3개 재현성 | 0.029 / 0.023 / 0.021 (안정적으로 양수) |

검증 구간과 실제 미래 구간 모두 양수로 나왔고, 세 개의 다른 랜덤 시드로 재학습해도 같은 방향으로
재현됐다 — 우연이 아니라는 근거로 삼았다.

### 3.3 라이브 운영 중 발견한 문제와 해결 과정

라이브로 올린 뒤 실제 데이터를 관찰하는 과정에서 두 단계의 문제를 발견하고 고쳤다. 이 과정 자체가
"모델이 그냥 잘 됐다"가 아니라 "문제를 데이터로 찾고 고쳤다"는 근거라서 발표에 넣을 만하다.

**1단계 — 서빙 버그 (10/5 수정)**: 학습 때는 항상 켜져 있던 이벤트 플래그(한국은행 금리결정일,
FOMC, 쿼드러플위칭 등 상태성 플래그) 컬럼이, 실제 서빙 코드에서는 당일 값이 0으로 비워져 들어가고
있었다. 즉 모델이 학습 때 한 번도 보지 못한 패턴을 실시간으로 입력받고 있었던 것. 발견 즉시
수정하고 재학습해 교체했다.

**2단계 — 특정 종목의 "얼어붙은" 출력 (10/6~ 관찰, 10/19 수정)**: 교체 후에도 5개 추론 종목 중
삼성바이오로직스·셀트리온 두 종목의 예측 확률이 입력이 크게 바뀌어도 거의 그대로였다(매수확률
표준편차 0.0055). 원인을 들여다보니 2.2절에서 언급한 TFT의 "정적 특성 분리 구조"가 역설적으로
문제였다 — 모델이 "오늘 무슨 일이 있었나"보다 "이 종목이 원래 어떤 종목인가"(정적 특성)에 과하게
의존하고 있었다. 세 가지 해법을 검토했고, **정적 특성 경로에만 별도의 weight decay(과적합 억제
기법)를 추가**하는 방법을 채택했다(`static_weight_decay=0.001`, 나머지 구조는 동일). 검증 성능은
거의 그대로(+0.0729, 기존 +0.0723 대비 오차범위 내)였지만, 문제가 됐던 종목의 반응성(종목별
일간 변화와 실제 순위 변화의 상관)은 뚜렷하게 개선됐다(삼성바이오로직스 기준 +0.464 → **+0.821**).
10/19 밤 교체했고, 이후 4거래일(10/20~10/23) 라이브 관찰로 확인했다.

## 4. 실제로 체결은 몇 건이었나 — 그리고 그게 무엇을 의미하는가

### 4.1 파이프라인 안정성 (버그가 있었는지)

모델 교체 전후 총 8거래일(10/6~10/8, 10/20~10/23)을 측정했다. **5분 주기 추론이 624/624회 전부
정상 실행됐고, 백엔드 전송 실패·파이프라인 오류는 0건**이다. 즉 "AI 추론 → 백엔드 전달" 구간은
완전히 안정적으로 동작했다.

### 4.2 그런데 실제 체결은 8거래일 내내 0건

이 결과만 보면 "시스템이 안 되는 것 아니냐"고 오해할 수 있어서, 별도의 읽기 전용 시뮬레이션으로
원인을 데이터로 분리했다(운영 코드는 건드리지 않고, 실제로 쌓인 5분봉과 실제 AI 예측을 그대로
재생). 세 가지 조건을 비교했다:

| 시나리오 | 조건 | 3일(10/6~10/8) 체결 가능 건수 (확신도 0.40 기준) |
|---|---|---|
| A. 지금 운영 그대로 | AI 확신도 + 전략 기술조건(추세·RSI·볼린저) 둘 다 충족 필요 | 0건 |
| C. 기술조건 숫자만 완화 | RSI·볼린저 기준값만 느슨하게 | 6건 |
| D. 기술조건 없이 AI 신호만 | 확신도 기준만 확인 | 8건 |

**해석**: 확신도 기준(0.40)을 0.35까지 낮춰도 지금 전략 그대로면 체결은 거의 늘지 않는다(3일 합산
4건). 반면 전략의 기술조건을 걷어내면 같은 확신도 기준에서 체결 기회가 8배로 늘어난다(0→8건).
**즉 체결이 안 나는 주된 이유는 AI 확신도가 아니라, 안전성을 위해 추가한 기술조건이 매우
보수적으로 설계되어 있기 때문**이다 — 실제로 종목당 두 달(8/1~10/8)에 기술적 신호가 12~29번만
발생했다. 10/19 모델 교체(evtfix→staticwd) 이후 4거래일(10/20~10/23)에서도 같은 결론이
재확인됐다.

**단, 이게 "기술조건을 없애는 게 더 낫다"는 뜻은 아니다.** 시나리오 D는 "체결이 가능했을 횟수"만
센 것이고, 그 체결들이 실제로 수익이었는지는 별도로 검증해야 한다(5절 "남은 과제" 참고). 이
프로젝트가 데이터로 입증한 것은 **"0건이 버그가 아니라 설계된 보수성의 결과"**라는 것과,
**"안전성(기술조건)과 체결 빈도 사이에 뚜렷한 트레이드오프가 존재한다"**는 것이다. 어느 쪽이
더 나은 설계인지는 수익성 데이터가 있어야 판단할 수 있다.

## 5. 남은 과제 (한계)

- **체결 빈도와 수익성은 별개다.** 지금까지는 "체결이 몇 번 가능했는가"만 셌고, 그 체결이
  수익이었는지는 검증하지 않았다. 체결가 기반 수익률 계산이 다음 단계로 남아있다.
- 정적 특성 과의존 문제는 완화(3.3절)했지만 근본 원인(라벨이 여전히 종목 고유 특성에 끌리는
  경향)은 남아있다. 변동성 관련 입력을 종목별로 정규화하는 다음 세대 레시피(`root_structure_volz`,
  OOT timing IC +0.0332로 지금까지 테스트한 모든 모델 중 최고)를 이미 찾아놨고, 다음 재학습
  사이클의 1순위 후보로 기록해뒀다.
- 두 가지 자금 배분 정책(`cap_cash` vs `redistribute`)의 실제 차이는 아직 비교 운영하지 않았다.
- 배포(실서비스화)는 이번 캡스톤 범위 밖으로 뺐다. 로컬 환경에서 전체 파이프라인이 끊기지 않고
  동작하는 것까지를 검증 범위로 잡았다.

## 6. 결론으로 쓸 수 있는 것

1. **"AI 추론 → 전달 → 자동매매 판단"까지 전 구간이 실제 장중 데이터로 끊김 없이 동작함을
   검증했다**(8거래일, 624/624회, 오류 0건).
2. **모델을 만드는 과정에서 생긴 두 가지 실제 버그/구조적 문제를 데이터로 발견하고, 근본 원인을
   진단하고, 여러 해법을 비교해서 고쳤다**(이벤트 플래그 서빙 버그, 정적 특성 과의존).
3. **체결이 0건인 이유를 "버그"와 "설계된 보수성"으로 데이터로 분리해서 증명했고, 안전성과 체결
   빈도 사이의 트레이드오프를 정량화했다.** 다만 이 트레이드오프에서 어느 쪽이 더 나은지는 아직
   모른다 — 그게 다음 단계다.
