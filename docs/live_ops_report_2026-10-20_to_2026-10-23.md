# 실시간 추론·자동매매 운영 리포트 (2026-10-20 ~ 2026-10-23)

staticwd 체크포인트(`v3_structure_nowd_cs-seed0-staticwd`)를 2026-10-19 밤에 실서버에
교체한 뒤, 첫 주(화~금) 실거래일 동안의 실시간 추론 파이프라인과 자동매매 루프 운영
현황을 정리한다. 모든 수치는 `Back-Gentle-Viking`의 `trading` DB
(`ai_prediction_history`, `auto_trade_decisions`, `trade_logs`)를 직접 조회해 확인했다.

## 1. 요약

- 4거래일(10/20~10/23) 내내 라이브 모델은 `v3_structure_nowd_cs-seed0-staticwd` 고정,
  모델 버전 혼선 없음.
- 추론 파이프라인: 10/21~10/23 매일 390건(5종목 × 78사이클) 정상 적재, 에러 0건.
  10/20은 전날 밤 장애 복구 후 교체 작업까지 겹쳐 자동매매 루프가 늦게 시작됐다(§3).
- 자동매매 루프: 10/21부터 안정적으로 하루 종일 가동. 전 구간 **실제 체결 0건**
  (기존부터 그랬던 `min_confidence=0.40` 임계값 미달이 원인, §4).
- 10/20 저녁 GPU 드라이버 행 때문에 재부팅 1회 발생 → watchdog이 백엔드를
  자동 재기동(17:15:09)했고, 재기동 후 자동매매 루프만 수동으로 다시 시작함(§5).
- `ops_check.sh`의 `preflight`/`open`/`close` 휴장일 판정이 이번 주 내내(그리고 그
  이전부터로 추정) 깨져 있었다는 사실을 이번에 처음 확인함 — 실거래에는 영향 없지만
  일일 점검 리포트 자체가 조용히 무력화된 상태였다(§6, 발견된 이슈).

## 3. 10/20 자동매매 루프 지연

10/16~10/19 서버 다운 사고(장애 보고서는 `progress.md` 참고) 복구 직후 10/19 밤에
staticwd 교체를 실행했고, 백엔드 프로세스가 그 과정에서 재시작됐다. `trading_loop`는
백엔드 메모리 내 `asyncio.create_task`로만 존재하므로 프로세스 재시작 후에는 누군가
`POST /trade/start`를 다시 호출해야 한다. 10/20 오전에는 이게 호출되지 않은 상태였고,
10/20 낮에 사용자 지시("니가 눌러")로 로컬 테스트 계정 JWT를 발급해 직접
`/trade/start`를 호출해 재가동했다. 이 때문에 10/20의 `auto_trade_decisions`는
5건뿐이고, 10/21부터 하루 전체 분량(300건대)이 쌓이기 시작했다.

## 4. 체결 0건인 이유

전체 `trade_logs`는 2026-10-05의 BUY 1건(FAILED, 스모크 테스트)이 유일하며, 이번 주
4일간 신규 체결은 없다. `auto_trade_decisions`의 `action`/`reason` 분포:

| 날짜 | SKIP·LOW_CONFIDENCE | SKIP·NO_MARKET_PRICE | HOLD·STRATEGY_CONDITION_NOT_MET | HOLD·NO_BUY_ALLOCATION |
|---|---|---|---|---|
| 10/20 | 3 | 2 | - | - |
| 10/21 | 142 | - | 190 | 13 |
| 10/22 | 380 | - | 5 | - |
| 10/23 | 213 | - | 102 | - |

이번 주 최고 확신도는 BUY 0.3990(10/23, 000660, `min_confidence=0.40` 미달로 SKIP),
SELL 쪽은 0.4484(10/23, 000660)까지 올라갔지만 보유 중인 포지션이 없어 `action=HOLD`
(매도할 물량 자체가 없음, `ultra_safe` 전략은 공매도를 하지 않음)로 처리됐다. 즉
체결 0건은 버그가 아니라 `ultra_safe` 전략의 `min_confidence=0.40` 임계값(3분류 모델의
최대 확률이 보통 0.35~0.42대라 사실상 거래가 거의 안 나오게 설계된 값, `app/schemas.py`
주석 참고)이 그대로 작동하고 있는 것이다. 모델 교체 전후로 이 동작에 차이는 없다.

## 5. GPU 드라이버 행 / 재부팅 (10/20 저녁)

10/20 저녁에 GPU 드라이버 행(`nvidia-modeset: Error while waiting for GPU progress`)이
재발해 사용자가 직접 재부팅했다(장 마감 후, 당일 EOD 배치 완료 확인 후). 재부팅은
학습/GPU 작업에만 영향이 있고 실시간 추론·자동매매는 CPU 전용이라 원칙적으로 무관하지만,
재부팅 자체가 백엔드·AI 서버 프로세스를 내려 watchdog이 재기동(`status.log` 10/20
17:15:09 "백엔드 재기동 성공")했고, 이번에도 `trading_loop`는 자동으로 복구되지 않아
수동으로 `/trade/start`를 다시 호출했다. 10/21~10/23 사이에는 추가 재부팅/재기동
없이 3일 연속 무중단으로 돌았다(`status.log`에 10/20 17시 건 외 재기동 기록 없음).

## 6. 발견된 이슈 (이번 리포트 작성 중 확인)

- **`ops_check.sh`의 `preflight`/`open`/`close` 모드가 이번 주 내내 전부
  `ModuleNotFoundError: No module named 'serving'`로 실패**하고 있었다. 원인은
  스크립트 23번째 줄의 휴장일 판정 호출이 `cd $REPO`와 `PYTHONPATH=.` 없이
  `python -c "from serving.market_calendar import ..."`를 실행하기 때문. 휴장일
  판정이 실패하면 "모르면 건너뛴다"는 설계상 안전한 방향으로 빠지기 때문에(장이
  열린 것처럼 진행해 거짓 FAIL을 내는 대신 그냥 skip) 실거래/추론에는 영향이 없었지만,
  결과적으로 매일 아침 preflight·장 시작 확인·장 마감 요약 점검이 10/20 이전부터
  (정확한 시작 시점 미확인) 쭉 조용히 동작하지 않고 있었다. `watchdog` 모드(5분 간격
  헬스체크/재기동)는 이 버그와 무관하게 정상 작동 중이었다.
  - **조치 완료(2026-10-24):** `ops_check.sh` 23번째 줄 호출을 `cd $REPO &&
    PYTHONPATH=.`를 붙여서 실행하도록 수정. 수정 후 동일 명령을 직접 실행해
    트레이스백 없이 `True`/`False`가 정상 반환되는 것을 확인했다(수정 당일이
    토요일이라 스크립트의 요일 체크에서 먼저 빠져나가 `status.log`에는 다음
    평일부터 반영됨). 다음 평일(월요일) 아침 `status.log`에
    `[WARN] ... 판정 실패` 줄 없이 `preflight`/`open`/`close`가 정상적으로
    OK/FAIL을 찍는지 재확인 필요.
